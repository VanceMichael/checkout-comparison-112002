# 结算页披露证据的逐会话比较的演练来源

这里提供独立来源的本地合成记录，与实际单位、个人和线上业务无关。

## 本地运行

使用 Node.js 22.23.4。先执行 `npm ci`，再执行 `npx playwright install chromium` 准备 Chromium。

执行 `npm test` 检查合成来源、浏览器页面和取证工具。执行 `npm start` 启动来源，默认监听 `127.0.0.1:4100`，可通过环境变量 `PORT` 调整端口。访问根路径可看到来源名和当前回放阶段。

服务地址下的 `/checkout` 为报价确认页。页面根据买家、商品、数量、取货方式和权益显示报价，不接受下单。控件修改会触发异步报价。不同页面会话各自保存草稿，报价时间为 UTC，金额为人民币元。

## 接口资料

| GET 路由 | 来源约定 |
| --- | --- |
| `/source/sampling` | 对照的两组会话独立。onlyDiff 是唯一计划改变的属性；同篮子指商品及数量、商户、取货方式、已选权益均相同。 |

查询参数 `offset` 是从零开始的页偏移，`limit` 默认 3，取值 1 至 100。响应中的 `records` 含 `record` 来源记录键、`availableFrom` 首次出现的回放阶段、`kind` 记录类型、`payload` 业务字段。来源记录键与业务身份分别定义。`next` 为下一页偏移，末页为 `null`。回放阶段中的记录按到达顺序可查。

控制员通过 `POST /control?stage=2` 切换到第 2 阶段，服务会保留更早已可查的记录。每次换阶段后按根路径返回的 `stage` 确认切换成功。

## 取证工具

`collect.mjs` 在授权的本地演练站按监测计划采集一组对照的报价证据，停在确认页，不提交订单。

```sh
node collect.mjs --port 0 --stage 1 --study Q-61 --out evidence/Q-61
# 或对接已启动的来源：
node collect.mjs --base http://127.0.0.1:4100 --study Q-62 --out evidence/Q-62
```

退出码：`0` 已生成比较记录；`2` 证据已留但不可比较（原因见 `run.json`）；`1` 运行错误。

### 采集方式

- **两组独立会话**：对照组与实验组各自使用新的浏览器上下文，草稿、篮子版本计数、页面会话互不共享；只有重新计算才会产生新报价。
- **只碰可见控件**：条件按监测计划通过页面控件设置，报价只从确认页可见文本读取；同时记录表单快照、`sessionStorage` 草稿和当次请求序列。
- **一篮子、一个对照条件**：计划校验 onlyDiff 是唯一改变项，其余条件在取证前与采到的证据中都要逐项相符。
- **晚回旧报价隔离**：页面只有一份报价列表，任何请求返回都会覆盖它。工具以“可见报价字段必须与当前表单一致、没有其他条件请求在途、页面已安静”为接受条件；若目标报价显示后又被旧条件的报价覆盖，关闭该上下文、隔离这次读取的请求序列，并用本轮剩余时间重采。
- **金额三种口径**：`value`（明确数值，含明确为零）、`unknown`（尚未返回 / 待核算）、`not-applicable`（不适用）。未知项不按零补齐，也不参与任何差额。
- **比较记录的条件**：两组证据均可用且未过期、篮子身份可证明一致、只有计划内一个属性不同、货架规则相同、有效期重叠且比较时刻落在共同有效期内、关键披露已经收到、报价等于分项之和。任一条不成立就不写 `comparison.json`。

### 产物

每轮目录下：

| 文件 | 内容 |
| --- | --- |
| `control.json` / `variant.json` | 各组证据：页面上下文、会话条件与草稿、篮子版本、货架规则、有效期、全部可见字段、每个金额的原文本/口径/选择器/时间/会话。一组失败或过期时另一组照常写出。 |
| `comparison.json` | 仅在可比时生成；同口径比较各金额，并给出差额（分为单位）。 |
| `run.json` | 整轮摘要：计划、阶段、两组是否仍有效、隔离记录、`holds`、不可比原因。 |
| `report.md` | 复核员可通读的摘要：每组的有效期、篮子版本、货架规则、会话条件、每个金额的原文/口径/定位/读取时刻，以及比较或不可比原因。 |

### 不可比原因

`run.json` 的 `comparison.reason` 与 `label` 会区分：

| reason | 含义 |
| --- | --- |
| `subject-mismatch` | 主体不对：商品、数量、商户或买家条件不一致 |
| `terms-differ` | 条款不同：取货方式、权益或货架规则等条件不一致 |
| `time-disjoint` / `evidence-expired` | 时间范围不重合；某组报价已过期 |
| `disclosure-missing` | 关键披露仍未收到（存在“尚未返回”的金额） |
| `rules-revised` | 对照期间货架规则改版，或计划当前受 `hold` 约束 |
| `evidence-incomplete` | 缺少一组证据或有效期，无法判断 |

### 已知边界

- 第 4 阶段 Q-62 的对照组报价有效期只有 900ms，采集完两组后通常已过期；此时只保留两组各自证据，不生成比较记录。复核时可用 `runRound({ compareAt })` 以指定时刻重新判定，证据不会被删改。
- 第 3 阶段起 Q-62 受 `hold` 记录约束（规则变更后需按新计划重新对照），即使两组页面字段一致也不会写成差异结论。
- 对照期间若站点切换取货方式导致运费不同，两组各自留证，但该轮无法并入原对照。
- 工具只覆盖当前演练站可观察到的字段；新增页面字段若影响 baskets 或条款判断，需要在 `lib/evidence.mjs` 的 `BASKET_KEYS` 与 `CONDITION_FIELDS` 中显式登记，未登记的字段不会被猜测。
